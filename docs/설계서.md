# 자재청구 관리 웹 프로그램 설계서

설계서 v1.6 · 2026년 10월 25일 · 파주 콘텐츠시티 현장

> 현행 구현 기준: 17~19절과 [작업인계](작업인계.md)를 우선한다. 1~15절의 초기 목업·관계형 데이터 모델·개발 순서는 당시 제안의 기록이며 모든 제안이 구현됐다는 뜻이 아니다. 운영 검증 완료 여부는 17절을 따른다.

## 1. 제안 요약

기계·소방 청구내역을 하나의 웹 프로그램에서 조회하고, 본사 제출용 엑셀을 추가해 내역을 갱신한다. 업체 연락처와 자재승인목록을 연결하여 청구 항목에서 거래처 확인까지 이어지도록 한다. 현재 웹 프로그램 구현과 GitHub 업로드까지 완료했다. 초기 목업 설명은 참고 이력이며 Vercel 자동 배포 연결 및 운영 배포 성공은 별도 확인이 필요하다.

첫 화면은 요청한 ‘청구내역 조회’로 한다. 별도 대시보드 메뉴를 늘리지 않고 기존 누적 항목 수와 공종별 항목 수를 상단에 표시한다. 조회 위주 PC 화면을 기본으로 하되 휴대폰에서는 핵심 항목 카드와 상세 화면을 제공한다.

## 2. 참고자료 확인 결과

| 파일 | 확인한 내용 | 프로그램 반영 방법 |
|---|---|---|
| 1.자재청구내역.xlsx | 자재청구내역서 시트: 11개 열, 품명 있는 데이터 331행. Sheet1과 메모·연락처 시트도 존재 | 11개 열을 조회 기본틀로 채택. 초기 전체 이력과 자동 합산하지 않음 |
| 2.전체 자재청구내역_1016.xlsx | 자재청구내역 시트: 1,983행, 기계 957행·소방 1,026행. 날짜 2026.05.08~2026.10.16. 확인사항 시트 포함 | 초기 누적 내역의 기준. 확인사항을 이관 검토자료로 함께 보존 |
| 3.추가 참고자료.xlsx | ‘10월 20일’ 시트의 번호·품명 있는 행 87행. ‘9월 11일(삭제16일재청구)’ 시트 19행 | 추가 업로드 형식. 재청구 표시 시트는 기본 제외하고 관리자가 판단 |
| 4.원자재,대리점 목록.xlsx | 기계·소방 승인목록과 각각의 연락처 시트. 번호·품명 있는 승인 품목은 기계 37행, 소방 52행 | 공종별 승인 품목 및 업체·품목 관계의 기준 |

집계는 데이터 행 기준이며 고유 자재 종류 수, 청구서 수, 총수량과 다르다. 승인 품목 행 수도 고유 제조사 수를 뜻하지 않는다. 원본 파일은 변경하지 않았다. 잠금용 임시파일(~$)은 분석 대상에서 제외했다.

중요한 발견:

- 전체 이력은 7열이다. 원자재·대리점·작업위치·신청자가 별도 열로 존재하지 않으므로 없는 값을 추정해서 채우지 않는다. 확인된 업체만 비고에서 연결하고 나머지는 ‘미등록’으로 둔다.
- 추가 청구서의 10월 20일 시트는 Q9가 ‘청구물량’, S9가 ‘누계’인데 첫 데이터의 실제 500은 S12에 있다. 열 이름만 믿거나 누계와 청구물량을 더하면 잘못된 수량을 가져올 수 있다.
- 추가 청구서 H6의 엑셀 날짜값 46315는 2026.10.20이다. 숫자형 날짜를 정상 변환하고 시트명·본문 날짜 불일치를 검사해야 한다.
- 전체 이력에는 날짜 불일치, 단위 누락, 추가메모 및 확인 표기가 있다. 기존 ‘확인사항’ 시트의 원본 행 연결을 유지한다.
- 비고에는 업체 외에도 ‘400/2’, 규격·색상·추가메모가 있다. 슬래시만으로 전부 업체 분리하면 안 된다.
- 승인목록 A·B·C·D는 후보 열로 보존한다. 승인 등급 또는 공급 우선순위라는 근거는 없다.

## 3. 화면과 기능

### 청구내역 조회

기본 열 순서: 분류 / 날짜 / 품명 / 규격 / 단위 / 수량 / 원자재 / 대리점 / 작업위치 / 신청자 / 비고.

공종 전체·기계·소방, 기간, 품명·규격·업체 통합검색, 원자재, 대리점, 신청자, 작업위치로 필터한다. 날짜 최신순이 기본이며 정렬·페이지 이동·열 너비 조절을 제공한다. 사용자가 선택한 조건을 엑셀로 내려받는다. 내보내기에는 필터 조건·출력시각·원본 추적 열을 포함할 수 있다.

행 상세에는 원본 비고, 원본 업체 표기, 연결된 표준 업체명, 업로드 파일·시트·행, 청구번호, 변경 이력, 연결 연락처, 승인목록 연결 상태를 표시한다. 서로 다른 단위를 합산하지 않는다. 같은 품명이라도 규격·단위가 다르면 별도 집계한다.

이력의 ‘등록됨’은 입고 완료가 아니다. 기존 파일에서 알 수 없는 납품·입고·발주 상태는 생성하지 않는다. 현재는 사용자가 확인해 입력하는 부분입고·입고완료·입고취소와 이력 보관을 구현했다. 원본 청구수량만으로 입고 여부를 추정하지 않는다.

### 업체연락처 조회

공종, 업체 역할(원자재/대리점/겸용), 업체명, 취급품목으로 검색한다. 업체별 여러 연락처·담당자·이메일·팩스·메모를 등록한다. 같은 대리점이 여러 원자재 및 품목을 취급하는 관계를 지원한다. 연락처 시트의 전화는 기본적으로 해당 대리점 연락처로 연결하고 제조사 직접 전화로 복제하지 않는다.

업체 상세에서 관련 청구내역과 승인 품목으로 이동한다. 모바일은 전화 연결, 이메일 복사·메일 앱 열기를 제공한다. 이메일 발송 이력 및 자동 발송 서비스는 초기 범위에 포함하지 않는다.

### 자재승인목록 조회

기계·소방 탭과 품목·제조사 검색을 제공한다. 원본 품목명과 A~D 후보 표기를 유지하면서 각 후보 업체를 연결한다. 한 품목에 여러 승인 업체와 선택적 증빙파일을 연결할 수 있다. 신규 등록·수정 시 등록자·수정일·변경 사유를 기록한다.

청구 품명과 승인 품목은 문자열이 다를 수 있으므로 ‘품목 연결표’를 관리한다. 연결된 승인 제조사와 일치하면 ‘목록 일치’, 아직 연결하지 못하면 ‘연결 미확인’, 연결된 품목의 제조사 후보와 다르면 ‘검토 필요’로 표시한다. 법적·최종 승인 여부를 자동 확정하지 않는다.

### 설정

업체·담당자·이메일 관리, 승인 품목·증빙 관리, 업체 별칭 관리, 가져오기 이력, 백업·복원, 사용자 권한을 탭으로 제공한다. 조회자는 조회·내보내기, 편집자는 청구서 검토·등록, 청구내역 수정, 업체연락처 수정, 자재승인목록의 오입력 정정을 수행한다. 관리자는 이 기능에 더해 승인 업체 후보 변경·증빙 교체 등 실제 승인 내용 변경, 사용자 관리·복원·업체 병합을 수행한다. 승인 내용 변경과 단순 오입력 정정은 별도 작업으로 구분하며 권한은 서버에서도 확인한다.

세 목록 모두 조회 화면의 행 또는 모바일 카드 상세에서 ‘수정’ 기능을 제공한다. 설정 화면을 거치지 않고 잘못 입력되거나 인식된 정보를 정정할 수 있다. 구체적인 수정 범위와 보호 규칙은 15절을 따른다.

## 4. 초기 데이터 이관 원칙

1. 2번 파일의 1,983행을 원본 추적 정보와 함께 기준 이력으로 이관한다. 공종별 건수와 날짜 범위를 대조한다.
2. 4번 파일에서 업체·연락처·승인 품목을 생성한다. 반복 업체명은 동일성 검토 후 연결하고, 업체 역할·공종·품목 관계를 분리한다. 빈칸은 임의로 윗행 값으로 채우지 않는다. 실제 병합된 셀만 병합 범위 기준으로 복원한다.
3. 1번 파일은 조회 양식 및 보강 후보로 사용한다. 2번 파일과 겹칠 수 있으므로 331행을 추가 이력으로 일괄 삽입하지 않는다. 날짜·공종·품명·규격·단위·수량을 대조해 연결 후보를 제시하고 사용자가 확인한 부가정보만 보강한다.
4. 3번 파일은 테스트용 미리보기에 사용한다. 10월 20일 87행을 자동 추가하지 않는다. 삭제·재청구 시트 19행은 기본 제외한다. 행별 수량·날짜·업체 연결과 중복 검토가 끝난 항목만 반영한다.
5. 확인 불가·누락 값과 기존 확인사항을 검토 대기 목록으로 넘긴다. 원본 비고 및 이미 정리된 이력을 덮어쓰지 않는다.

## 5. 엑셀 추가 업로드 상세

파일 선택 → 시트 선택 → 공종·청구일·청구번호 확인 → 열 연결 및 수량 미리보기 → 업체 변환·중복 검토 → 반영 항목 확인 → 저장 결과 순서로 진행한다.

지원 형식은 우선 제공된 .xlsx 두 종류(정리표/본사 청구서)로 한정한다. 임의 양식은 열 연결 화면을 거친다. 실제 배포 전 파일 크기 제한은 테스트 결과와 사용 요금제에 맞춰 확정한다. 파일 확장자와 실제 형식, 압축 해제 한도, 행수 한도를 검사하고 수식·매크로는 실행하지 않는다.

청구서 형식의 기본 추출 후보는 C열 품명, I열 규격, L열 단위, T열 비고, U열 작업위치, V열 신청자다. 수량 열은 시트별 선택값으로 저장한다. 제목 위치와 반복되는 표 구조를 탐지하고 행 번호와 품명이 있는 실데이터만 추출한다. 제목·결재·서명·인쇄용 여백은 제외한다. 원본 청구번호의 기계/소방 표기와 선택 공종이 다르면 확인을 요구한다.

날짜는 Excel 1900/1904 날짜 체계와 텍스트 날짜를 처리한다. 본문 날짜를 우선 후보로 사용하되 시트명과 다르면 사용자가 확정한다. 날짜가 없으면 연도를 임의 확정하지 않는다. 원본 수량 값·수식·저장된 계산 결과를 구분하고, 계산 결과가 없는 수식은 재계산된 파일 또는 직접 확인을 요구한다. 수량은 소수도 저장하며 음수·빈값·문자 혼입은 검토 대상으로 둔다.

파일 단위 SHA-256과 현장 ID로 동일 파일 재등록을 차단한다. 내용이 달라진 재업로드는 공종+청구번호+항목번호, 그리고 날짜+품명+규격+단위+수량의 보조 비교로 후보를 찾는다. 기존 이력에 청구번호가 없는 경우 보조 비교는 경고만 하며 자동 삭제하지 않는다. 실제 반복 청구는 별도 내역으로 유지할 수 있다.

저장은 서버에서 다시 검증하고 하나의 데이터베이스 트랜잭션으로 확정한다. 업로드 작업 ID를 재사용해 더블클릭·네트워크 재시도로 중복 저장되지 않게 한다. 일부 행만 반영하는 경우 적용·보류·제외 건수와 사유가 합계로 일치해야 한다. 보류 행은 다음 검토에서 이어서 처리한다. 가져오기 취소는 이력을 보존하는 상태 변경으로 처리하며 후속 수정이 있으면 충돌을 확인한다.

## 6. 업체명 정규화 규칙

원본 표기와 연결 결과를 별도 보관한다. 표준명은 사용자 확인 및 4번 목록을 기준으로 한다. ‘에스제이/세종’은 사용자가 지정한 예대로 원자재 ‘에스제이’, 대리점 ‘세종넷피아’로 연결한다. ‘세종’의 별칭을 저장해 이후 같은 표기에 적용한다.

앞뒤 공백·중복 공백을 정리해 후보를 검색한다. 슬래시 양쪽이 등록 업체/별칭이고 원자재·대리점 관계에 맞을 때만 자동 연결 후보로 만든다. 일반 메모·분수·규격은 그대로 둔다. ‘정도’처럼 축약 표기의 정확한 업체가 확인되지 않은 경우 후보를 제시하고 사용자가 선택한다. 표기가 같아도 여러 법인이면 자동 병합하지 않는다. ‘㈜에스제이’와 ‘에스제이’도 동일성 확인 없이 통합하지 않는다.

별칭은 현장·역할·연결 업체·확인자·확인일을 보관하며 충돌 시 자동 적용을 중단한다. 업체명 수정은 연결 ID를 유지하므로 과거 청구의 연결은 보존되고 원본 표기도 남는다.

| 청구 항목 | ID, 청구서 ID(과거자료는 선택), 공종, 날짜, 품명, 규격, 단위, 수량 decimal, 원자재 ID, 대리점 ID, 작업위치, 신청자, 현재 비고, 원본 비고, 수정 출처, 최종 수정자·시각, 상태, 버전 |
| 업체 / 담당자 | 업체 ID, 표준명 / 역할·공종 관계 / 담당자 이름·전화·팩스·이메일·메모 |
| 공급 관계 | 현장 ID, 품목 ID, 원자재 업체 ID, 대리점 업체 ID |
| 승인 품목 / 후보 | 품목 ID, 현장 ID, 공종, 원본 품목명 / 업체 ID, 원본 후보열, 증빙파일 ID |
| 품명 연결 / 업체 별칭 | 청구 품명·규격→승인 품목 / 원본 표기→업체 ID, 역할, 확인자 |
| 업로드 / 원본 행 | 파일 해시, 저장 위치, 파일명, 양식 / 시트, 행 번호, 원본 셀 값, 열 연결 설정, 검토 상태 |
| 변경 기록 | 대상 ID, 이전·변경 값, 사용자, 시각, 사유, 작업 유형(수정/정정/되돌리기), 버전, 작업 ID |
| 백업 기록 | 형식 버전, 생성 시각, 현장 ID, 파일 목록, 건수, 체크섬, 수행자 |

청구 항목 한 행이 하나의 청구 이력이다. 동일 품명·규격이 여러 날짜에 반복되어도 합쳐 저장하지 않는다. 업체와 승인 품목의 관계는 다대다로 구성한다. 기계·소방 선택값은 제한하고 모든 조회·수정은 현장 ID로 접근 범위를 제한한다. 동시 편집은 버전 번호로 충돌을 감지한다.

## 8. GitHub · Vercel · Supabase 운영 구성

데이터 저장은 사용자 요청에 따라 Supabase로 확정한다. 청구내역·업체연락처·자재승인목록·별칭·수정 이력은 Supabase PostgreSQL에, 원본 엑셀·승인 증빙·백업 파일은 Supabase의 비공개 Storage에 저장한다. 로그인은 Supabase Auth를 사용한다. 웹 화면 및 서버 API는 Next.js + TypeScript, 배포는 GitHub와 연결한 Vercel 구성을 제안한다. Supabase 요금제와 보관 용량은 운영 규모에 맞춰 구현 시 정한다.

흐름: 사용자 브라우저 → 로그인 → 웹/API 권한 확인 → 현장별 데이터베이스 및 비공개 파일 저장소. 업로드 분석은 미리보기로 시작하고 서버가 확인된 데이터와 원본을 검증해 저장한다. 큰 파일의 장시간 처리는 작업 큐 또는 분할 처리를 적용할 수 있도록 업로드 작업 상태를 분리한다.

GitHub는 소스코드와 데이터베이스 변경 스크립트를 관리한다. 원본 청구서·연락처·백업·운영 비밀키는 저장소에 넣지 않는다. Vercel에는 환경변수로 연결 정보를 등록한다. 관리자 권한의 비밀키는 서버에서만 사용한다. 저장소 변경과 Vercel 연결로 웹 배포를 구성하고, 데이터는 외부 영구 저장소에 유지한다. Vercel의 파일 영구 저장은 객체 저장소를 사용하는 구성이 공식 안내에 부합한다.

조회·편집·관리자 권한은 화면 숨김에만 의존하지 않고 서버와 데이터베이스 정책에서 함께 검사한다. Supabase의 데이터 및 파일 접근 정책을 현장 권한에 맞춘다. 미리보기 배포는 운영 DB와 분리하고 변경 스크립트를 시험한 후 운영에 적용한다. 초기화·복원은 관리자만 실행한다. 로그인 없이 열리는 공개 조회는 기본 제공하지 않는 것을 제안한다.

## 9. 백업과 복원

전체 백업은 버전 명세 JSON, 청구·업체·담당자·승인·별칭·매핑 데이터, 원본 엑셀과 증빙, 파일별 체크섬을 포함한 묶음으로 한다. CSV/엑셀 내보내기는 조회 편의용이며 전체 복원을 대신하지 않는다. 인증 비밀번호·로그인 토큰·환경변수는 백업에 넣지 않는다. 사용자는 별도 계정 체계로 유지하고 복원 시 사용자 연결 누락을 보고한다.

복원은 파일 형식·버전·체크섬·참조 관계 검사 → 격리된 임시 영역에서 검증 → 현재/복원 데이터 건수 비교 → 현재 상태 자동 백업 → 관리자 확인 → 해당 현장 전체 교체 순서로 한다. v1은 합치기 복원을 지원하지 않아 중복 위험을 줄인다. 검증 실패 또는 파일 누락 시 교체하지 않는다. 교체 동안 쓰기를 잠그고, DB와 파일은 복원 작업 버전으로 묶어 모든 준비가 끝난 뒤 활성 버전을 전환한다. 실패 시 이전 활성 버전을 유지한다.

삭제 대신 보관 상태를 사용하고 변경 이력을 남긴다. 백업은 암호화된 보관 위치와 관리자의 접근 제한을 적용한다. 수동 전체 백업을 v1에 포함하고 정기 자동 백업은 운영 주기·보관기간을 합의한 후 추가한다. Supabase 기본 DB 백업에는 Storage의 실제 파일이 포함되지 않으므로 원본·증빙 파일도 별도로 백업해야 한다.

## 11. 개발 순서와 추가 제안

1단계는 Supabase 연결·로그인·공종별 조회·초기 이관·연락처·승인목록과 세 목록의 개별 수정 및 수정 이력을 구현한다. 2단계는 실제 두 엑셀 형식의 업로드 미리보기, 업체 별칭, 중복 검토와 반영 이력을 구현한다. 3단계는 전체 백업·복원·권한 검증·실제 배포 검증을 완료한다. 초기에 수량 열과 업체명 연결 결과를 충분히 검토해야 이후 업로드가 안정된다.

추가 아이디어는 ‘확인 필요한 항목’ 필터, 자주 찾는 검색조건 저장, 청구 항목에서 업체 연락처 바로 열기다. 실제 입고수량 기록과 본사 청구서 작성·엑셀 생성은 구현했다. 납기·미입고 알림·자동 이메일 발송은 후속 검토 항목이다.

구현 전 확정하면 좋은 운영 항목: 사용자 수와 권한 담당자, 같은 업체의 법인명 통합 기준, 청구서 수정본 처리 기준, 백업 보관기간, 승인 증빙파일 필요 여부. 이번 설계는 한 현장에 여러 사용자가 로그인해 사용하는 방식을 기본 가정으로 했다.

## 14. 반응형 웹 필수 요구사항 (추가 반영)

PC와 휴대폰에서 같은 주소와 같은 데이터를 사용하는 반응형 웹을 필수로 개발한다. 모바일은 별도 앱 설치 없이 브라우저에서 사용한다. 기존 본문의 모바일 방향은 선택 기능이 아닌 필수 범위로 확정한다.

- 360~767px: 휴대폰. 메뉴는 상단에 배치하고 검색·입력폼은 한 열로 표시한다. 요약 카드는 두 열, 청구내역은 카드 목록으로 바꾼다. 품명·공종·날짜·규격·수량과 단위를 우선 노출하고 업체·작업위치·신청자·비고도 확인할 수 있게 한다. 실제 구현에서는 상세 펼치기를 제공한다.
- 768~1199px: 태블릿. 두 열 배치를 여유에 맞게 줄이고 긴 표는 표 내부에서 가로 스크롤한다. 본문 전체에 가로 스크롤이 생기지 않게 한다.
- 1200px 이상: PC. 좌측 메뉴와 11열 청구내역 표, 상세 패널을 사용한다.
- 연락처와 승인목록의 긴 표는 휴대폰에서 카드 또는 핵심 열+상세로 구현한다. 현재 목업의 해당 표는 내부 가로 스크롤로 확인하는 예시다.
- 버튼과 주요 터치 영역은 최소 44px 높이로 하고, 검색·날짜 선택·파일 업로드·편집·백업 다운로드·복원을 터치로 수행할 수 있어야 한다. 파일 업로드는 휴대폰의 파일 선택기를 사용한다.
- 업체 전화는 전화 앱 연결, 이메일은 복사 및 메일 앱 열기를 지원한다. 마우스 올리기에만 의존하는 기능은 만들지 않는다.
- 표의 가로 스크롤을 제외하고 360/390/430/768/1024/1440px 폭에서 본문 잘림이 없어야 한다. 세로·가로 방향 전환과 화면 키보드 표시 시 입력란과 저장 버튼을 사용할 수 있어야 한다.
- iPhone Safari와 Android Chrome에서 로그인, 조회, 필터, 행 상세, 엑셀 선택·검토·업로드, 다운로드를 실제 기기로 점검한다. 모바일 백업 복원도 관리자 권한 및 동일 검증 절차를 적용한다.

추가 산출물: 390px 폭의 휴대폰 청구내역 및 설정 목업 PNG. HTML은 창 너비에 따라 실제로 레이아웃이 바뀌며 데이터 저장 기능은 없는 시안이다.


## 15. 청구내역·업체연락처·자재승인목록 수정 기능 (필수)

### 공통 수정 절차

조회 목록에서 항목 선택 → 상세 보기 → 수정 → 원본과 현재 값 비교 → 입력값 검증 → 수정 사유 입력 → 저장 → 목록·검색·집계 갱신 순서로 처리한다. 잘못 입력한 값과 엑셀 자동 추출·업체 연결의 오인식을 사용자가 직접 정정할 수 있어야 한다. 업로드 미리보기에서 저장 전에 수정할 수 있고, 이미 등록된 자료도 다시 수정할 수 있다.

PC에서는 상세 패널 또는 편집 창, 휴대폰에서는 화면 너비에 맞는 단일 열 편집 화면을 제공한다. 저장·취소 버튼을 명확히 구분하고 저장하지 않은 변경이 있을 때 화면을 벗어나면 알린다. 저장 실패 시 입력 내용을 유지하며 완료 메시지는 실제 저장이 성공한 뒤 표시한다. 개별 수정은 초기 필수 기능으로 한다. 일괄 수정은 후속 기능으로 두며 개별 수정만으로 세 목록의 모든 정정 업무가 가능해야 한다.

### 청구내역 수정

분류(기계/소방), 날짜, 품명, 규격, 단위, 수량, 원자재, 대리점, 작업위치, 신청자, 비고의 11개 업무 항목을 수정할 수 있다. 날짜·수량 오인식, 업체 분리 오류, 누락 값도 직접 보완할 수 있다. 수량은 단위와 함께 확인하고 숫자 형식과 공종·날짜 등 필수값을 검증한다. 기존 이력의 단위·규격 누락은 임의 채우기를 강제하지 않고 ‘미확인’ 사유와 함께 보존할 수 있다.

원자재·대리점은 등록 업체에서 선택하고, 미등록 업체는 권한에 따라 새로 등록하거나 미확인 상태로 남긴다. 업체명 정정과 다른 업체로의 연결 변경을 구분한다. 품명·규격·원자재 수정 후 승인목록 연결 상태와 중복 후보를 다시 계산한다. 공종·날짜 수정 후 필터와 요약 건수도 다시 반영한다. 청구서에 연결된 항목의 공종·날짜는 청구서 정보와 일치하는지 검사하고, 청구서 전체를 변경할지 개별 항목을 정정할지 영향 범위를 확인한다. 청구서 전체 변경은 관련 항목과 함께 일관되게 저장한다.

화면과 내보내기는 사용자가 저장한 최신 값을 사용한다. 원본 파일·원본 셀 값·최초 추출값·원본 비고·원본 위치는 별도로 보존하고 일반 편집에서 변경할 수 없다. 비고 정정은 ‘현재 비고’를 변경하며 원본 비고는 비교 화면에서 확인한다.

### 업체연락처 수정

업체명, 역할, 적용 공종, 취급품목, 담당자, 전화, 휴대전화, 팩스, 이메일, 메모 및 공급 관계를 수정한다. 여러 담당자·연락처를 추가하거나 사용 종료 상태로 바꿀 수 있다. 이메일 형식을 검증하고 전화번호는 원래 표기를 보존하면서 검색용 정리 값을 함께 관리한다.

동일 업체의 이름 정정은 업체 ID를 유지하고 연결된 청구내역·승인목록에 최신 이름을 표시한다. 반면 청구내역의 업체 연결 오류 정정은 선택한 항목의 업체 ID만 바꾼다. 두 작업 모두 영향받는 연결 건수를 저장 전에 안내하고 원본 업체 표기는 유지한다. 다른 업체와 중복되는 이름으로 변경할 경우 경고하며 자동 병합하지 않는다. 업체 병합은 관리자 별도 기능으로 분리한다. 사용 중인 업체는 일반 수정 과정에서 영구 삭제하지 않는다.

### 자재승인목록 수정

공종, 품목명, 제조사 후보 A~D 연결, 비고, 증빙파일과 품명 연결표를 수정할 수 있다. 원본 후보열과 원본 품목 표기는 남긴다. 단순 오탈자·오인식 정정과 실제 승인 내용 변경을 선택하도록 하며, 단순 정정 유형에서는 승인 업체 후보 교체나 증빙 교체를 허용하지 않는다. 승인 내용 변경은 관리자 권한으로 처리하고 변경 사유와 근거자료를 기록한다. 공종·품목 변경도 실제 승인 범위에 영향을 주면 관리자 작업으로 처리한다.

정정은 기존 원본에 맞게 현재 데이터를 바로잡는 작업이다. 실제 승인 내용이 바뀌면 새 버전을 생성하고 적용 시작일을 기록한다. 과거 청구에 연결된 승인 버전은 유지하며, 현재 목록 기준의 재검토는 별도 표시한다. 항목 수정 후 관련 청구의 연결 상태를 갱신하되 과거의 승인 결과를 일괄 덮어쓰지 않는다.

### 오인식 재발 방지 및 수정 보호

사용자가 업체 연결 오류를 정정하면 ‘이번 항목만 수정’과 ‘이후 업로드에 적용할 별칭 규칙도 등록’을 구분한다. 별칭 등록은 기존 충돌·연결 영향을 확인한 뒤 저장한다. 한 항목 수정만으로 과거 전체 자료나 이후 추출 규칙이 자동 변경되지 않게 한다.

재업로드·재분석은 사용자가 수정한 값을 자동 덮어쓰지 않는다. 원본 값, 마지막 추출값, 사용자 확정값을 비교해 차이 목록을 만들고 행별·필드별로 유지 또는 교체를 선택한다. 원본 추적 ID와 청구 항목 ID는 수정해도 유지하여 수정 후에도 재업로드 중복 검사가 가능하게 한다.

### 수정 이력·되돌리기·동시 편집

누가, 언제, 어떤 항목을, 어떤 값에서 어떤 값으로, 왜 변경했는지 기록한다. 업무 데이터와 수정 이력을 Supabase PostgreSQL의 동일 트랜잭션으로 저장하고 서버가 사용자·시간을 확정한다. 수정 이력은 일반 사용자에게 직접 변경·삭제 권한을 주지 않는다. 증빙 교체 시 파일을 새 경로로 먼저 저장하고, DB 확정 후 새 파일을 연결한다. 실패한 업로드는 정리하고 이전 파일은 보존한다.

권한 있는 사용자는 이전 값으로 되돌릴 수 있다. 되돌리기도 새로운 변경 기록으로 남기며 이력을 삭제하지 않는다. 관련 업체·승인 관계가 달라져 이전 값이 유효하지 않으면 사유를 표시하고 직접 검토하도록 한다. 저장 시 읽어 온 버전과 현재 버전을 비교하여 다른 사용자의 수정이 있으면 저장을 중단하고 변경 내용을 보여준다. 네트워크 재시도는 작업 ID로 중복 이력 생성을 방지한다.

### Supabase 저장 및 권한 기준

세 목록의 현재 값·원본 추출값·검토 상태·변경 기록·버전 정보를 Supabase PostgreSQL에 저장한다. 원본과 증빙은 Supabase 비공개 Storage를 사용한다. 브라우저의 임시 저장이나 Vercel의 로컬 파일은 업무 데이터의 기준 저장소로 사용하지 않는다. PC에서 저장한 수정은 휴대폰에서 다시 조회할 때도 동일하게 나타나야 한다.

Supabase Auth의 로그인 사용자와 현장별 권한을 기준으로 서버 및 RLS 정책을 검사한다. 조회자는 수정할 수 없고 편집자는 세 목록의 허용된 정정을 수행한다. 관리자만 실제 승인 내용 변경·복원·업체 병합을 수행한다. 승인 버전 및 이력 기록은 직접 테이블 수정을 막고 검증된 서버 작업 또는 데이터베이스 함수로만 변경한다. Storage에도 현장별 파일 접근 정책을 적용한다.

### 추가 완료 확인 기준

- 세 목록에서 저장 전 미리보기 정정과 등록 후 개별 수정이 가능하고, 취소하면 기존 값이 유지될 것.
- 날짜·수량·업체 연결을 잘못 추출한 사례를 직접 정정하고 목록·집계·내보내기에 최신 값이 반영될 것.
- 같은 파일 재분석과 수정본 업로드가 사용자 정정값을 자동 덮어쓰지 않을 것.
- 업체명 정정과 다른 업체로의 연결 변경의 영향 범위가 정확하고, 원본 및 수정 전후 값이 보존될 것.
- 승인 내용 변경은 관리자만 실행하고 과거 연결 버전과 신규 적용일이 구분될 것.
- 동시 수정·저장 실패·재시도·되돌리기에서 데이터와 변경 이력이 일치할 것.
- PC와 휴대폰에서 수정·저장·취소·이력 확인이 가능하고 재조회한 결과가 Supabase의 저장값과 일치할 것.

이번 개정은 설계서에만 반영했다. 기존 목업은 수정 기능 추가 전의 시안이며 수정 버튼과 편집 화면은 본 절의 요구사항에 따라 구현한다.


## 16. 자재별 집계 및 누적 청구수량 (2026-10-23 추가)

### 메뉴와 검색
- 새 메뉴 ‘자재별 집계’를 추가한다. 모바일 하단 메뉴에서도 접근한다.
- 품명·규격·단위 검색, 전체/기계/소방, 시작일·종료일 필터를 제공한다. 기본값은 전체 기간이다.
- 자재명순, 최근 청구순, 청구 항목 많은순으로 정렬한다.
- 리스트 열: 품명, 규격, 단위, 총청구수량, 기계 수량, 소방 수량, 청구 항목 수, 수량 미확인 건수, 최근 청구일.
- 행 선택 시 날짜별 청구 이력을 표시하며 개별 청구 상세로 연결한다. 조회 조건과 집계 결과를 엑셀로 내려받는다.

### 집계 기준
- 현재 선택한 현장의 삭제되지 않은 청구내역만 집계한다. 기존 현장 접근 권한을 그대로 적용한다.
- 품명·규격·단위가 같은 항목을 묶는다. 대소문자와 앞뒤·연속 공백을 정규화한다. 약칭 추정이나 규격·단위 자동 변환은 하지 않는다.
- 다른 규격과 단위는 별도 행으로 표시한다. 단위가 섞인 전체 수량 총합은 제공하지 않는다.
- 청구 항목 수는 엑셀 행 기준이며 청구서 파일 수가 아니다. 기본 합계는 기계·소방 합산이며 공종별 수량을 함께 표시한다.
- 수량 미확인 값은 합계에서 제외하고 건수를 표시한다. 모두 미확인이면 ‘미확인’으로 표시하며 실제 0과 구분한다.
- 원본의 음수 조정은 누적 합계에 반영한다. 이력에서 양수 청구와 음수 조정 합계를 따로 표시한다. 소수는 최대 다섯 자리로 계산한다.
- 수정·삭제·복원 후 현재 데이터 기준으로 다시 계산한다. 별도 집계 저장 테이블이나 기존 사이트의 테이블 변경은 필요하지 않다.

### 상세화면
- 현재 비고 바로 아래 ‘누적 총청구수량’을 표시한다. 동일 품명·규격·단위의 전체 기간, 기계·소방 합산 수량이다.
- 목록 검색기간과 관계없이 전체 기간을 사용한다. 청구 항목 수, 미확인 건수, 조정 수량 및 전체 이력 버튼을 제공한다.
- 누적 청구수량은 실제 입고량을 뜻하지 않는다. 실제 입고는 기존 입고 현황에서 확인한다.

### 추가 아이디어
- 이번 반영: 기계·소방 수량 비교, 최초·최근 청구일, 개별 청구 이력 연결, 엑셀 출력.
- 후속 검토: 월별 청구 추이, 작업위치별 집계, 관리자가 확인한 자재명 통합표. 이름이 비슷하다는 이유만으로 자동 병합하지 않는다.

### 검증 기준
- 규격·단위가 다른 행 분리, 소수 합산, 음수·0·미확인 구분, 삭제 항목 제외를 확인한다.
- 기간·공종 필터 및 상세화면 전체 기간 합계가 각각 올바르게 적용되는지 확인한다.

### 16.1 여러 자재 선택 후 청구내역 함께 보기
- 집계 목록에 항목별 체크박스와 검색 결과 전체 선택, 선택 해제, 선택 내역 보기 버튼을 제공한다.
- 같은 품목을 다른 이름으로 청구한 경우 사용자가 원하는 항목을 선택하여 날짜순 청구내역을 함께 조회한다. 원본 품명이나 저장 데이터는 변경하지 않는다.
- 선택 내역에서 원래 품명·규격·날짜·공종·수량·작업위치·신청자·대리점을 표시하고 개별 상세화면으로 연결한다.
- 합계는 규격·단위별로 나누고 기계·소방 수량 및 미확인 건수를 표시한다. 다른 규격·단위는 한 숫자로 합산하지 않는다.
- 현재 조회의 기간·공종 조건을 적용하며 검색조건을 제출하거나 초기화하면 선택을 해제한다. 선택 자체는 영구 저장하지 않는다.

### 16.2 담은 자재 보관 및 엑셀 출력
- 검색 결과를 체크하고 ‘선택 자재 담기’로 보관한다. 다른 검색을 수행한 뒤 계속 추가할 수 있다. 같은 품명·규격·단위는 중복 담지 않는다.
- ‘담은 자재’에서 개별 제거, 모두 비우기, 한꺼번에 내역 보기, 엑셀 내려받기를 제공한다.
- 담은 목록은 브라우저 저장소에 현장·사용자별로 보관하며 새로고침 후 유지한다. 다른 기기와 자동 공유하지 않으며 브라우저 저장소를 지우면 사라진다.
- 담은 목록은 현재 검색조건과 별도로 전체 기간의 최신 청구내역을 조회한다. 원본 데이터는 변경하지 않는다.

### 16.3 업로드와 검색 편의 개선

## 17. 2026-10-24 구현 확정 사항 (현행 우선)

### 17.1 메뉴와 작성 흐름

현재 메뉴는 청구내역 조회, 청구서 작성, 업체연락처 조회, 자재승인목록 조회, 자재별 집계, 설정이다. 청구서 작성 화면은 왼쪽 자재 검색과 오른쪽 촘촘한 입력 표로 구성한다. 품명·규격·단위가 같은 기존 청구내역은 자재 검색에서 한 종류로 표시하므로 누적 청구 건수와 검색 자재 종류 수가 다르다.

품명·규격·단위·수량·대리점·작업위치·신청자·구분을 표에서 편집한다. 수량 Enter는 다음 품목으로 이동한다. 다운로드는 각 품목의 양수 수량만 필수이며 다른 칸은 비어 있어도 된다. 다운로드 자체는 업무 청구내역 등록이 아니며 기존 업로드 검토·확정 절차를 사용한다.

새 작성 시 한국시간 오늘을 청구일로 설정한다. 입고요청일은 청구일 +2일, 금요일만 +3일이며 다른 요일의 주말·공휴일 보정은 없다. 청구일 변경 시 다시 계산하고 직접 수정도 허용한다. 기본정보와 공통 입력은 접힌 상태로 시작한다.

### 17.2 작성용 엑셀 불러오기와 제출 양식

작성 화면의 엑셀 불러오기는 기존 본사 양식과 제목 기반 일반 표를 지원한다. 일반 표는 ‘품명’만 있어도 되며 규격·단위·수량·대리점·작업위치·신청자·구분은 선택이다. 순서는 자유이며 없는 값은 추정하지 않는다. 시트·품목 수를 확인해 기존 목록 뒤에 추가한다. 품명 없는 행은 제외하며 중복 후보를 자동 삭제하지 않는다.

제한은 .xlsx 15MB, 시트 10,000행, 작성 목록 최대 500품목이다. 기존 본사 양식의 제목·본문 병합·서식·열 너비·인쇄 설정을 보존한다. A~T열만 본사 인쇄 범위이며 Q 수량, T 대리점, U 작업위치, V 신청자, W 구분을 사용한다. U~W는 내부 기록용으로 인쇄 범위 밖에 둔다. 보조 영역 U14:U15·V52:W52의 병합만 독립 행 입력을 위해 해제했다. 제공된 예시값과 상품 이미지는 출력 양식에서 제거했다.

### 17.3 선택 합산 출력

‘같은 품목 합산하여 다운로드’ 체크 해제 시 원래 행을 출력한다. 체크 시 품명·규격·단위·대리점·구분이 모두 같은 행의 수량을 합산한다. 작업위치·신청자는 중복을 제외하고 ` / `로 연결한다. 기계와 소방은 절대로 서로 합산하지 않는다. 서로 다른 단위·대리점도 분리한다. 이 기능이 공종별 파일 자동 분할을 의미하지는 않는다.

합산 파일은 ‘작성 상세내역’ 시트에 위치별 원본 행을 보관한다. 재업로드 시 이 시트를 우선해 위치별 수량을 복원하며 합산 시트와 함께 이중 등록하지 않는다. 작성 중인 표 원본은 다운로드 합산으로 바뀌지 않는다.

### 17.4 작성리스트 관리와 저장

설정에 ‘작성리스트 관리’를 둔다. 신청자·작업위치·단위 목록을 등록·수정·삭제·검색하고 기존 이력에서 가져온다. PC에서는 두 열의 작은 목록 패널과 내부 스크롤, 좁은 항목 높이를 사용한다. 작성 화면은 목록 선택과 자유 입력을 모두 허용하며 자유 입력값을 관리 목록에 자동 등록하지 않는다. 목록 변경은 과거 청구자료와 이미 작성된 값에 소급 적용하지 않는다.

실제 저장 구조는 7절의 초기 분리 테이블 제안과 다르다. Supabase의 `mm_projects`, `mm_members`, `mm_records`, `mm_audit`, `mm_operations` 및 비공개 `mm-files` 버킷을 사용한다. 업무 객체는 `mm_records.kind`와 JSON 데이터로 보관한다.

## 21. 청구 취소·삭제 (2026-10-29)
- 상세화면에서 청구 취소와 삭제를 구분한다. 취소는 업체 전달 후 취소 이력을 남기는 전체 항목 취소이며 사유·처리자·시각을 보관한다. 업체에 자동 통보하지 않는다.

- 삭제는 requestArchived 표시로 목록에서 숨기고 삭제 목록에서 복구한다. 원본·입고·변경 이력은 보존한다. 취소 해제와 삭제 복구는 각각 사유를 기록하며 삭제 복구만으로 청구 취소를 해제하지 않는다.
- 조회자는 변경하지 못하며 기존 편집 권한·버전 충돌·감사이력·백업 구조를 사용한다. 신규 SQL 설치는 필요하지 않다. 기존 요청 JSON의 requestCancellation, requestArchived, requestStateHistory를 사용한다. 현재 앱의 입력 검증과 독립 DB 권한 검증을 운영 DB 검증과 구분한다.

- 입출고 표를 관리 버튼에 맞춰 1,275px로 조정하고, 최근 처리순 버튼을 화면 끝이 아닌 표 관리 열의 끝선에 맞췄습니다. 좁은 화면은 가로 스크롤을 사용합니다.
- DB 테이블/SQL 변경은 없으며 기존 batch 공도구 데이터에 포함됩니다. 실제 운영 Supabase의 사진 저장 및 타기기 조회는 별도 확인이 필요합니다.
