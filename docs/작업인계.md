# 자재청구 관리 작업인계

작성일: 2026-10-24 (한국시간)  
저장소: https://github.com/jojuntae-hash/material  
기준: 프로그램 커밋 `31d2b08` 및 이 문서와 함께 갱신한 설계서  
목적: 집 컴퓨터에서 수행한 작업을 회사 컴퓨터의 새 Codex 대화에서 이어가기

## 1. 회사 컴퓨터에서 시작하기

1. 저장소를 처음 사용할 경우 clone하고, 이미 있다면 현재 수정사항을 확인한 뒤 `git pull`로 최신 코드를 받는다. 로컬 변경을 임의로 초기화하지 않는다.
2. Node.js 22 이상, pnpm 11.25 이상을 준비한다. 저장소 루트에서 다음 명령을 실행한다.

```sh
pnpm install --frozen-lockfile
pnpm dev
```

3. 개발 서버는 http://127.0.0.1:5173/ 이다. 이미 같은 포트를 쓰는 서버가 있으면 실행 여부를 먼저 확인한다.
4. 공유 자료를 사용하려면 기존 Supabase 계정으로 로그인하고 같은 현장을 선택한다. 공개 연결 설정은 `src/public-config.js`에 있으며 환경변수·브라우저 설정이 우선한다. 비밀키는 프런트엔드에 넣지 않는다.
5. 새 Codex 대화에 아래처럼 요청한다.

> docs/작업인계.md, docs/설계서.md, README.md와 현재 코드를 읽고 이 프로젝트를 이어서 작업해줘. 회사에 있는 별도 설계서를 제공하면 현재 구현과 대조해 수정하되, 과거 설계의 미구현 제안을 완료된 기능으로 취급하지 마.

`localhost`는 각 컴퓨터 내부 주소다. 집의 실행 서버나 브라우저 임시저장 내용이 회사 컴퓨터로 자동 이전되는 것은 아니다. 이 문서는 작업 맥락을 전달하며 대화 전체를 복제하지 않는다.

## 3. 이번 작업에서 확정한 기능

### 청구서 작성

- 메뉴에 ‘청구서 작성’을 추가했다. 왼쪽은 기존 자재 검색, 오른쪽은 작성 목록이다.
- 검색 후보는 품명·규격·단위별로 묶는다. 누적 청구 항목 수와 자재 종류 수는 다르다. 사용자 화면에서 확인했던 2,122건/1,558개는 당시 자료 기준이며 고정값이 아니다.
- 품목을 하나씩 추가하고 촘촘한 표에서 품명·규격·단위·수량·대리점·작업위치·신청자·구분을 수정한다. 수량 칸 Enter는 다음 품목 수량 칸으로 이동한다.
- 새 청구일은 한국시간 오늘이다. 입고요청일은 청구일 +2일, 금요일만 +3일이다. 다른 요일의 주말·공휴일은 별도 보정하지 않는다. 청구일을 바꾸면 입고요청일도 다시 계산하며 직접 수정할 수도 있다.
- 청구서 기본정보는 기본 접힘이다. 공통 입력값을 새로 추가하는 품목이나 전체 품목에 적용할 수 있다.
- 다운로드에는 각 행의 양수 수량이 필요하다. 대리점·작업위치·신청자·단위 등 다른 칸은 비어 있어도 된다.
- 작성 초안은 현장·모드·사용자별 브라우저 localStorage에 보관하며, 다른 기기로 자동 공유하지 않는다.
- 다운로드만으로 업무 청구내역에 등록되지 않는다. 파일을 기존 업로드 검토 흐름으로 가져와 확정해야 한다.

### 엑셀 불러오기와 양식 보존

- 작성 화면의 ‘엑셀 불러오기’는 기존 본사 양식과 간단한 `.xlsx` 표를 지원한다. 15MB 이하, 시트 10,000행 이하이며 한 작성 목록에는 최대 109개 품목을 허용한다.
- 간단한 표는 ‘품명’ 제목만 있어도 된다. 규격·단위·수량·대리점·작업위치·신청자·구분 등은 선택이며, 열 순서는 자유다. 없는 값은 추정하지 않는다.
- 시트와 품목 수를 확인하고 현재 작성 목록 뒤에 추가한다. 품명 없는 행은 제외한다. 중복 항목도 위치별 반복 입력일 수 있으므로 자동 삭제하지 않는다.
- 원본 양식의 본문 셀 병합, 서식, 열 너비, 인쇄 설정을 유지하도록 XLSX ZIP 내부의 입력 셀만 수정한다. 전체 양식을 SheetJS로 다시 저장하는 방식으로 바꾸지 않는다.
- 본사 인쇄 범위는 A~T열이다. 수량 Q열, 대리점 T열, 작업위치 U열, 신청자 V열, 구분 W열을 사용한다. U~W는 의도적으로 인쇄 범위 밖에 둔다.
- 독립된 품목 정보를 기록하도록 보조 영역 U14:U15·V52:W52의 병합만 해제했다. 사용자가 입력한 예시는 양식 위치를 설명하기 위한 자료이므로 실제 새 청구서 내용으로 남기지 않았다.

### 같은 품목 합산 다운로드

- 체크박스를 해제하면 입력한 행 그대로 출력한다. 체크하면 품명·규격·단위·대리점·구분이 같은 행의 수량을 합산한다.
- 작업위치와 신청자는 중복을 제거하고 ` / `로 연결한다.
- 기계와 소방은 절대로 서로 합산하지 않는다. 대리점이나 단위가 달라도 별도 행이다. 현재 기능은 구분별로 파일 자체를 자동 분할하는 기능은 아니다.
- 합산 출력 시 ‘작성 상세내역’ 시트에 원래 위치별 행과 수량을 보관한다. 시스템 재업로드와 작성 화면 재불러오기는 이 시트를 우선 선택해 위치별 정보 손실과 이중 등록을 피한다. 합산 시트와 상세 시트를 모두 같은 이력으로 등록하지 않는다.
- 작성 중인 표 자체는 합산으로 덮어쓰지 않는다.

### 설정 → 작성리스트 관리

- 신청자·작업위치·단위를 직접 등록·수정·삭제·검색하고 기존 청구내역에서 가져올 수 있다.
- 좁은 행, PC 2열 배치, 목록 내부 스크롤을 사용한다. 화면 전체를 길게 늘리는 큰 입력 카드로 되돌리지 않는다.
- 청구서 작성에서는 세 항목 모두 직접 입력하거나 관리 목록에서 선택한다. 직접 입력한 값을 관리 목록에 자동 등록하지 않는다.
- 대리점 선택 목록은 삭제되지 않은 업체 중 역할에 ‘대리점’이 있는 업체에서 가져온다. 업체연락처 화면에서 등록·수정한다.
- 선택 목록 삭제·수정은 기존 청구내역이나 이미 작성된 값에 소급 적용하지 않는다.

## 4. 저장과 Supabase에 관한 핵심 인계

| 대상 | 저장 | 기기 간 유지 |
|---|---|---|
| 공유 업무자료·입고·이력 | Supabase | 같은 현장 권한으로 로그인 후 조회 |
| 작성리스트 관리의 신청자·위치·단위 | 공유 모드는 Supabase, 로컬 모드는 IndexedDB | 공유 모드에서만 다른 기기에서도 사용 |
| 작성 중 청구서 초안 | localStorage | 해당 브라우저만 |
| 담은 자재·개인 정렬 | localStorage | 해당 브라우저만 |

작성리스트 목록은 기존 `mm_records`의 `kind='batch'`, `data.type='composer-lists'`인 레코드로 보관한다. 현장별 고정 ID는 `a8f791c2-15cc-4a52-997d-9899a9f5ab01`이며 `applicants`, `locations`, `units` 배열을 저장한다. 기존 `mm_apply` 저장·권한·버전·감사이력 체계를 사용하므로 이번 기능을 위한 별도 SQL 설치는 필요하지 않다. ‘가져오기 이력’에서는 이 설정용 batch를 제외한다. 새 batch 처리 코드를 만들 때도 설정 레코드를 실제 업로드 이력으로 오해하지 않는다.

기존 Supabase가 설치된 환경에서 `setup.sql`을 다시 실행하지 않는다. 실제 운영 계정의 저장·다른 기기 조회는 이번 세션에서 확인하지 않았다. 코드 연결과 독립 DB 권한 테스트가 통과한 것과 실제 운영 검증을 구분한다.

## 5. 검증·배포 상태

- 프로그램 최신 기준 커밋 `31d2b08`을 GitHub `main`에 push했다. 본 인계 문서 커밋은 그 다음 커밋이다.
- 최종 프로그램 검증: `pnpm test` 40개 통과, `pnpm build` 성공.
- `scripts/qa-request-composer.cjs`로 별도 브라우저의 테스트 자료를 사용해 검색, 품목 추가/수정/삭제, 날짜 계산, 초안 복구, 엑셀 불러오기/재출력, 선택 목록 관리, 합산 출력, 모바일 본문 넘침을 확인했다.
- 브라우저 검증 스크립트는 Playwright와 Windows Edge를 사용한다. `WORKSPACE_NODE_MODULES`로 Playwright 위치를 지정하거나 Codex의 번들 런타임 경로를 사용한다. 테스트 산출물은 무시되는 `test-results/`에 둔다.
- GitHub 업로드 완료와 Vercel 배포 완료는 다르다. 자동 배포 연결·실제 운영 URL·최신 배포 성공 여부는 아직 확인하지 않았다.
- 실제 휴대폰 Safari/Chrome, 운영 Supabase 로그인·권한·저장·복원에 대한 전체 검증은 남아 있다. 로컬 테스트로 운영 DB를 수정하지 않았다.

## 6. 회사의 별도 설계서에 반영할 내용

저장소의 `docs/설계서.md`는 이번에 v1.4로 갱신했다. 회사 컴퓨터에만 있는 별도 문서는 이 세션에서 열거나 수정하지 않았다. 회사에서 별도 문서를 제공한 뒤 아래 항목을 대조한다.

1. 범위를 ‘목업/개발 제안’에서 ‘구현된 웹 프로그램 + 운영 미검증 항목’으로 구분한다.
2. 청구서 작성 메뉴, 입력 표, 날짜 기본값, 수량만 필수인 다운로드를 반영한다.
3. 품명만 있는 간단한 엑셀과 기존 병합 양식의 불러오기를 구분해 기술한다.
4. A~T 본사 인쇄 범위와 U~W 내부 추적 정보의 용도를 명시한다.
5. 선택 합산 기준, 기계/소방 분리, 위치·신청자 병기, 상세 시트 재업로드 우선 규칙을 추가한다.
6. 작성리스트 관리 세 종류와 Supabase 설정 레코드 구조, 초안의 브라우저 전용 저장을 추가한다.
7. 이미 구현된 입고·취소·집계·담은 자재를 후속 제안으로만 남겨두지 않는다.
8. DB 설치 완료·배포 성공·운영 검증 완료는 근거 없이 확정하지 않는다. 현재 자료 건수도 과거 참고자료 수치와 구분한다.

기존 문서의 원본 근거·업무 판단·미구현 제안은 보존하고 구현 현황과 구분한다. 특히 사용자별 현재 이름·현장 자료·연락처를 문서 예시로 새로 복제하지 않는다.

## 7. 작업 시 지켜야 할 사항

- 프로그램의 실제 동작, 사용자 제공 양식과 정확한 입력 위치를 우선한다. 위치별 상세 자료를 잃는 편의 기능을 만들지 않는다.
- 기계·소방 청구서는 본사에 따로 제출하는 업무다. 공종 간 합산은 금지한다.
- 과도한 여백·큰 카드 대신 수십 개 품목을 빠르게 확인하는 촘촘한 표를 유지한다.
- 원본 자료·백업·로그인 토큰·비밀키를 GitHub에 올리지 않는다. `private-data/`, `.env.local`, `test-results/`는 무시된다.
- 양식 재생성은 `python scripts/prepare-request-template.py "원본 양식 경로"`를 사용한다. 원본 경로는 회사에서 제공해야 하며 원본 자체는 저장소에 없다.
- 대화에서 향후 수정이 요청되지 않은 별도 기능을 완료된 것처럼 기록하지 않는다. 새 변경 후에는 관련 테스트와 빌드, 필요한 화면 검증을 수행한다.
